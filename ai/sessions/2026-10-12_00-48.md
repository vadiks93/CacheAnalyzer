# Session recap - 2026-10-12 00:48 Europe/Chisinau

## Questions and answers

- **Can middleware tell whether a GET/QUERY response is streamed or buffered?** Not reliably from the HTTP method, Controller versus Minimal API, Content-Length, or number of writes/flushes. Endpoint opt-in is preferable for known finite responses.
- **Does CacheAnalyzer buffer responses?** The current ASP.NET Core adapter forwards each write to the original response stream first, then captures a separate bounded copy for analysis. It does not wait for the entire response before forwarding writes.
- **What does forwarding flushes mean?** The wrapper delegates Flush/FlushAsync to the original destination. The analysis copy remains intact. This does not guarantee immediate delivery through server/proxy buffers.
- **Where is the size limit configured?** `CacheAnalyzer.Core/CacheAnalysisOptions.cs`: MaximumPayloadBytes defaults to 3 * 1024 * 1024 bytes (3 MiB). Override via AddCacheAnalyzer(options => ...) or Configure<CacheAnalysisOptions>(builder.Configuration.GetSection("CacheAnalyzer")) with MaximumPayloadBytes in appsettings.json.
- **What if another layer has already buffered a 20 MiB response?** CacheAnalyzer forwards all 20 MiB to preserve the payload. Passing the span to destination.Write does not itself allocate another complete copy in CacheAnalyzer; the destination can have its own buffers. CacheAnalyzer cannot undo allocations made by other layers.
- **Can analysis capture stop at the limit?** It already does. CaptureForAnalysis checks declared Content-Length and accumulated size before copying a chunk. An oversized single chunk is not copied. A chunk that would exceed the limit discards any previous capture, sets ExceededLimit, and stops subsequent capture; all response bytes continue to be forwarded.
- **Where is the analysis buffer?** `CacheAnalyzer.AspNetCore/LimitedResponseBuffer.cs`: private readonly MemoryStream _responseBytesForAnalysis. This is distinct from destination, the original response stream.
- **Why not fingerprint only the first 3 MiB?** That would miss differences later in the payload. Oversized responses are skipped for fingerprint analysis instead.

## Important qualifications

- Headers, status, and payload must be preserved. Analysis adds setup/copying/allocation/hashing overhead and can affect timing. Hashing happens after the downstream pipeline returns; indefinite streams cannot be fingerprinted until they finish.
- MaximumPayloadBytes bounds per-response capture, not total memory or concurrent requests. Eligible responses allocate an additional byte-array copy for fingerprinting. QUERY request-body buffering is separate.
- Explicit response start/completion, file sending, and custom response body features have not been validated for all combinations. Keep latency-sensitive streaming endpoints outside analysis.
- The .NET Framework sample adapter differs: it buffers the whole response before checking size.
