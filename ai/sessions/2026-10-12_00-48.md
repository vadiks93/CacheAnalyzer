# Session recap - 2026-10-12 00:48 Europe/Chisinau

## Questions and answers

- **Are RequestId and Fingerprint both fingerprints/hashes?** Yes, both are SHA-256 hashes. RequestId hashes the full request identity (method/URL/query and QUERY body hash/content metadata) to separate histories and correlate findings without raw parameters. Fingerprint hashes response bytes to detect matching/changing output. The same RequestId can have different response fingerprints over time. RequestId is currently logged by default; response Fingerprint remains opt-in.

- **Are in-memory hashes safe on the client's server with no outbound calls?** Hashes/history/candidates live in the host application's managed process memory; repository runtime source search found no outbound HTTP/socket code or explicit fingerprint file persistence. This is not a dependency/host audit: configured logging providers and custom sinks can export data. Managed memory can appear in process/crash dumps or OS paging; temporary response captures can appear too, and clearing/disposal does not securely erase bytes. Hosting/dump access is controlled by the client. State the boundary as local in-process analysis with no built-in outbound transport, not guaranteed RAM-only or inaccessible storage.

- **Are fingerprints one-way hashes?** Confirmed built-in Sha256ResponseFingerprintProvider computes SHA-256 over response bytes and encodes the digest with Base64URL. SHA-256 has no decryption/reversal operation; finding an arbitrary original input is computationally infeasible. Predictable low-entropy payloads can still be guessed and hashed for comparison, and matching hashes reveal matching payloads. Hashing is not encryption or guaranteed anonymization; default log exclusion remains useful.

- **Are all seven logger arguments part of State?** Yes: arguments map in placeholder order to RequestKey, Cacheable, Recommendation, PayloadBytes, FingerprintMilliseconds, Fingerprint, and TrackingCapacityReached, respectively.

- **Does the message template actually produce JSON State fields?** Yes with the configured JSON console provider. Re-read a log captured from the running sample, parsed it with ConvertFrom-Json, and confirmed State contains RequestKey, Cacheable, Recommendation, numeric PayloadBytes/FingerprintMilliseconds, Fingerprint, boolean TrackingCapacityReached, and OriginalFormat. ILogger preserves template arguments as structured state; no sentence parsing is involved. Other providers/exporters control their own serialization schema.

- **Can middleware tell whether a GET/QUERY response is streamed or buffered?** Not reliably from the HTTP method, Controller versus Minimal API, Content-Length, or number of writes/flushes. Endpoint opt-in is preferable for known finite responses.
- **Does CacheAnalyzer buffer responses?** The current ASP.NET Core adapter forwards each write to the original response stream first, then captures a separate bounded copy for analysis. It does not wait for the entire response before forwarding writes.
- **What does forwarding flushes mean?** The wrapper delegates Flush/FlushAsync to the original destination. The analysis copy remains intact. This does not guarantee immediate delivery through server/proxy buffers.
- **Where is the size limit configured?** `CacheAnalyzer.Core/CacheAnalysisOptions.cs`: MaximumPayloadBytes defaults to 3 * 1024 * 1024 bytes (3 MiB). Override via AddCacheAnalyzer(options => ...) or Configure<CacheAnalysisOptions>(builder.Configuration.GetSection("CacheAnalyzer")) with MaximumPayloadBytes in appsettings.json.
- **What if another layer has already buffered a 20 MiB response?** CacheAnalyzer forwards all 20 MiB to preserve the payload. Passing the span to destination.Write does not itself allocate another complete copy in CacheAnalyzer; the destination can have its own buffers. CacheAnalyzer cannot undo allocations made by other layers.
- **Can analysis capture stop at the limit?** It already does. CaptureForAnalysis checks declared Content-Length and accumulated size before copying a chunk. An oversized single chunk is not copied. A chunk that would exceed the limit discards any previous capture, sets ExceededLimit, and stops subsequent capture; all response bytes continue to be forwarded.
- **Where is the analysis buffer?** `CacheAnalyzer.AspNetCore/LimitedResponseBuffer.cs`: private readonly MemoryStream _responseBytesForAnalysis. This is distinct from destination, the original response stream.
- **Why not fingerprint only the first 3 MiB?** That would miss differences later in the payload. Oversized responses are skipped for fingerprint analysis instead.

## Important qualifications

- Headers, status, and payload must be preserved. Analysis adds setup/copying/allocation/hashing overhead and can affect timing. Hashing happens after the downstream pipeline returns; indefinite streams cannot be fingerprinted until they finish.
- MaximumPayloadBytes bounds per-response capture, not total memory or concurrent requests. Eligible responses allocate an additional byte-array copy for fingerprinting. QUERY request-body buffering is separate.
- Explicit response start/completion, file sending, and custom response body features have not been validated for all combinations. Keep latency-sensitive streaming endpoints outside analysis.
- The .NET Framework sample adapter differs: it buffers the whole response before checking size.

- **Does CacheCandidate repeat on subsequent calls?** Yes. Each eligible analyzed response is evaluated again using the current fingerprint, retained observation count, and payload-to-fingerprint ratio. If those conditions still hold, it is reported as CacheCandidate again, including another Information log through LoggingResponseAnalysisSink. It is not a permanent classification or a one-time notification. Changed responses or expired evidence can change the recommendation; bypassed analysis produces no new recommendation. Verified in InMemoryResponseFingerprintHistory.Observe and CacheAnalyzerMiddleware.InvokeAsync.
